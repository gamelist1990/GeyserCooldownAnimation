# Vibrant Visuals: 三人称の輪郭の試作

## 現在の基準: ユーザーが表示改善を確認した試作 8

2026-10-12、ユーザーが試作 8 に対して「おっイケてる！」と報告しました。
添付写真では胴体・脚の内側の白塗りが消え、背後の壁が見えています。
この条件での改善を確認した基準として試作 8 を維持します。
防具の全パターン、複数プレイヤーの重なり、通常描画モードでの互換性まで
確認できたという意味ではありません。画像では頭と腕にも白い領域が残っており、
防具を含む全面的な品質評価は別途必要です。

本番の Cooldown は `GeyserCooldownAnimation-1.3.15-vv-prototype.8.jar`、
Glowing は `0.2.13` です。配布 pack UUID は
`d5b7151e-a851-4e2f-89cf-0e3743d82708`。
候補の生成スクリプトは `build_vv_legacy_outline_prototype.py --forward-mask`。
再生成時は新しい UUID になるため、現在の実機確認済みファイルも保持します。
この報告を受けた追加のサーバー差し替えや再起動は行っていません。

これは修正済みリリースではありません。安定版のソースは維持しています。
ユーザーのテスト導入指示を受け、本番には試作版を入れています。

## 実機での結果と次の切り分け

試作 1 はユーザーの Vibrant Visuals で「自身が全体光るだけ」になりました。
輪郭方式が成功したとは扱いません。

試作 2 は polygon の頂点順だけを反転します。モデル寸法・法線・PBR
テクスチャ・通常の深度判定・一人称の処理は試作 1 のままです。
Bedrock の表面判定とモデル座標上の向きの違いを切り分ける候補です。
試作 2 でも全身が埋まる場合、この hull 方式を成功したものとして継続せず、
VV でのカリングや描画順の調査に戻ります。

## 調査結果

## 試作 3: 従来のアルゴリズムに戻す

試作 2 もユーザーの実機で改善しませんでした。ユーザーの指定で、
試作 3 は安定版 1.3.15 の従来アルゴリズムを使います。

```sh
python3 scripts/build_vv_legacy_outline_prototype.py \
  --extension-source build/libs/GeyserCooldownAnimation-1.3.15.jar
```

従来の細分化された輪郭モデル・UV・テクスチャ・身体、防具、マント、
エリトラの輪郭条件・色指定・壁越しの深度条件を維持します。
試作 1/2 の poly_mesh と PBR 全面発光テクスチャは含めません。
一人称の材質は従来定義を残し、三人称だけ追加の材質別名を使用します。

輪郭の追加材質は `entity_static` の代わりに `entity_alphablend` を継承し、
元の stencil / 反転カリングを維持して `ALPHA_TEST` を明示します。
`stencilReadMark` を `stencilReadMask` に訂正し、読み書きマスクを 32 と指定、
輪郭側の書き込みは 0 にします。これらが VV で有効かは未確認です。
公式資料では stencil 関連のキーは ignored と記載されているため、
この調整で VV 対応が保証されるとは扱いません。

モデル・テクスチャ・アニメーションは安定版 pack とバイト一致を生成時に
要求します。モデルの省略や別の輪郭アルゴリズムへの置き換えはありません。

### 当初の調査

### 試作 4: スキンとマスクの描画を分ける

試作 3 の写真では外形が白く表示され、スキンは見えていません。
写真だけでは、通常の身体が欠落しているのか、輪郭レイヤーが身体を
覆っているのかは確定できません。

`--separate-body-mask` を付けると試作 4 を生成します。
通常の三人称の身体を `Material.default` で描き、その直後に同じ
`Geometry.default` / `Texture.default` / part_visibility のマスク専用描画を追加します。
マスクは色・深度を書かず、深度判定成功時だけ stencil を書く設計です。
その後に従来の輪郭を描きます。一人称と輪郭モデルは変更しません。

これは身体の描画経路を独立させる切り分けです。VV が stencil を無視する場合は、
白い輪郭レイヤーが身体を覆う現象をこの変更だけで解消できません。
発光なしの三人称が正常かもユーザーに確認中です。

### 診断版 5: 発光状態のまま通常のスキン描画を確認

試作 4 でもユーザーは「見えない、形はスキン」と報告しました。
マスク分離だけでは改善していません。ここで材質の盲目的な調整を止め、
`--diagnose-skin-only` で三人称の outline controller 条件を `0.0` にした診断版を作ります。
身体・防具・マントは三人称で通常の材質を使用します。一人称は維持します。
発光の効果・サーバー側のプロパティ・スキンの取得処理は変更しません。

これは意図的に三人称の輪郭を一時停止した診断版です。修正版ではありません。
発光した状態でスキンが見えれば、問題は身体の消失よりも overlay 側に絞れます。
まだ見えなければ、通常のプレイヤー描画やスキン反映を調べる必要があります。

### 試作 6: 輪郭の後にスキンを合成

診断版 5 でユーザーが「見える」と確認しました。
通常のスキンは描画できています。白い overlay の内側が除去されないことが
問題と考えられ、プレイヤーモデルの欠落とは区別します。

`--repaint-skin` は試作 3 の従来の輪郭描画を復帰し、最後に通常の
`Geometry.default` / `Texture.default` でスキンを追加描画します。
追加材質は `entity_alphablend` + `ALPHA_TEST`、`depthFunc: Always`、
`DisableDepthWrite` とし、Stencil を使わず内側をスキンで覆う試験です。
モデル・アニメーション・一人称の制御は維持します。

これは従来の Stencil が VV で復旧したことを意味しません。追加材質の
深度条件や描画順が VV で反映されるかは未確認です。
まず防具なしでスキンと外周が同時に見えるかを確認します。
成功しても壁越しにスキンまで見える可能性、防具や透明なスキン、身体の
交差部分の合成を検討する必要があり、完成版として扱いません。

### 試作 7: スキン再描画の深度だけを変更

ユーザーの写真と報告で、試作 6 はスキンと輪郭が同時に表示できることを確認。
一方、プレイヤー本体も壁越しに見えています。追加スキン描画の
`depthFunc: Always` がその原因です。

`--depth-test-repaint` は試作 6 の追加スキン描画の `depthFunc` だけを
`LessEqual` に変更します。新しい pack UUID / 試作番号以外は同じです。
地形で隠れる身体のスキンを追加描画しないようにする試験です。
手前にいるときのスキン・外周と、壁に隠れたときのスキンを確認します。

輪郭側の壁越し描画は維持しています。Stencil が正常に働かないままなら、
身体が壁に隠れた場所では、白い発光レイヤーが全面に残る可能性があります。
試作 7 は本体の壁越し描画の切り分けであり、壁越しの純粋な輪郭まで
完成したという意味ではありません。

### 試作 8: 半透明材質によるマスクを輪郭の直前に追加

試作 7 はユーザーの写真で本体の壁による遮蔽が成功。しかし遮蔽部分の
白い発光レイヤーは残っています。通常の身体の深度判定と輪郭内側の除外を
別の問題として扱います。

`--forward-mask` は試作 7 のスキン描画を維持し、最初の輪郭 controller の
直前に `Geometry.default` / `Texture.default` を使ったマスク描画を追加します。
材質を輪郭と同じ `entity_alphablend` 系にし、opaque の身体の stencil が
別の pass に持ち越されることに頼らない構成を試します。

追加描画は `depthFunc: Always` で壁に隠れた身体の領域にも stencil 32 を
書き、`DisableColorWrite` と `DisableDepthWrite` で色・深度は変更しない設計です。
輪郭の表・裏面とも `NotEqual` にして、マスクの内側を除外します。
Stencil のキーが実際に VV で反映されるか、controller 指定順が実描画順と
一致するかは未確認であり、成功の保証はありません。

本体のスキンは引き続き通常の深度判定です。一人称、輪郭モデル、
テクスチャ、アニメーションは試作 7 と同じです。まず防具なし・柵による
部分遮蔽で、遮られた内側の白い面が消え外周だけ残るかを確認します。

従来の輪郭は `EnableStencilTest` / `StencilWrite` / `InvertCulling` と
拡大モデルを組み合わせています。Vibrant Visuals で全身が白くなる写真は、
内側を隠すマスクまたは反転カリングが効かない場合の表示と整合します。
クライアントの描画ログがないため、原因の断定はしていません。

Microsoft の [material の説明](https://learn.microsoft.com/en-us/minecraft/creator/documents/material-files?view=minecraft-bedrock-stable)
は stencil 関連の一部の項目を deprecated / ignored と記載しています。
[Vibrant Visuals の説明](https://learn.microsoft.com/en-us/minecraft/creator/documents/vibrantvisuals/introvibrantvisuals?view=minecraft-bedrock-stable)
では PBR の描画経路を使います。

## 試作の方式

- 各部位に内向きの面を持つ `poly_mesh` を生成。
- 材質は組み込みの `entity_alphatest`。独自の stencil、反転カリング、
  `depthFunc: Always` は新しい輪郭では使わない。
- 通常の身体の描画と深度判定で内側を隠し、拡大分を外周に残す設計。
- 発光は専用の PBR texture set の emissive チャンネルで指定。
- 最初は防具なしの頭・胴・両腕・両脚のみ。細分化した従来モデルは使わない。
- 一人称の描画条件、スクリプト、アニメーション、武器 attachable は維持。
  剣位置が直った `player.entity.json` の `min_engine_version` 不在も維持。
- 通常版とは別 UUID。試作は VV 専用パックであり、描画モードの自動判定はしない。

`poly_mesh` は [公式 schema](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/schemasreference/schemas/minecraftschema_geometry_1.14.0?view=minecraft-bedrock-stable)
でも experimental です。実際の Bedrock で面の向き、カリング、深度、PBR
が期待通りに動くかは未確認です。生成に成功しても見た目の修正成功を意味しません。

## 生成

```sh
python3 scripts/build_vv_outline_prototype.py \
  --extension-source build/libs/GeyserCooldownAnimation-1.3.15.jar --revision 2
```

`build/vv-outline-prototype/` に独立した `.mcpack` と、同じパックを埋め込んだ
試験環境用 JAR を作成します。JAR の Java 処理は安定版のままです。
本番へのコピー、再起動、GitHub リリースは行いません。

## クライアントで見る箇所

試験環境で安定版の Cooldown JAR を候補 JAR に置き換え、Glowing 0.2.13
を併用します。Cooldown がパックを所有する構成なので、独立した Glowing
パックは追加しません。クライアントは新 UUID のパックを取得して再接続します。
既存サーバーへのグローバル RP 追加だけでは、サーバー RP の優先度によって
上書きできない可能性があります。

まず Vibrant Visuals を有効にして、防具なし・発光ありの三人称の正面、
背面、斜め、歩行時を見ます。身体の模様が見え、外周だけに色が出るかが最初の判定です。
発光なしで余分なモデルが消えることと、一人称の剣位置・クールダウンも確認対象です。
全身が白い場合は面の向きまたはカリング、全く輪郭がない場合は mesh の
読み込み・面の向き・描画順をクライアントの Content Log で調べます。

## 未対応・制限

防具、マント、エリトラの専用輪郭、複雑なカスタムスキン、壁越し表示は未対応です。
半透明の発光 alpha は出し分けのみで、中間値の透過は再現しません。
チームの標準 16 色は専用テクスチャで表現し、任意の RGB は 64 色に近似します。
透明なスキンの穴や身体の交差部分では、余分な線が見える可能性があります。
見た目が確認できるまで、安定版を置き換える候補にはしません。
